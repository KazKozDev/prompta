Аудит Prompta и план развития

Чего не хватает генератору промптов, какие современные подходы ему нужны и в каком порядке за них браться. Приоритеты расставлены по соотношению эффекта и трудозатрат.

1Что было доступно для анализа

Анализировалось рабочее дерево: последний коммит плюс много незакоммиченных изменений и новых файлов (pipeline/limit.ts, pipeline/sources.ts, desktop/mcp_settings.py, catalog/source-excerpts.ts, SpeedDesk/). Поэтому выводы касаются не только опубликованной версии.

Прочитано: README корня, pipeline/ и eval/; eval/rubric.md; код пайплайна (index.ts, llm.ts, brief.ts, synthesize.ts, official.ts), eval/run.ts, eval/audit.ts, mcp/server.ts; CI; статистика каталога: 89 техник, из них 64 готовых, 18 процедур, 7 только в индексе.

Не проверялось: поведение во время работы (живые вызовы моделей не запускались), desktop/app.py целиком (3 544 строки), содержимое наборов правил и снимков официальных гайдов, SpeedDesk/.

2Текущее состояние

Prompta превращает сырой поток мыслей в готовый промпт. Точек входа три: десктоп-приложение на PyQt, CLI и MCP-сервер с инструментами improve_prompt и suggest_next_prompts.

  • Каталожный режим. Бриф → детерминированный отсев техник по типу задачи, бюджету и офлайн-режиму → выбор самой дешёвой подходящей с обязательным объяснением, почему не дешевле → синтез по шаблону. Рядом всегда строится zero-shot для сравнения.
  • Режим официальных целей (Claude, ChatGPT, Gemini, Grok, открытые модели). Промпт строится только по сохранённым правилам с версией, датой проверки, хешем и проверкой хостов источников.

Что стоит сохранить: строгий разбор JSON с повтором, трассировку шагов, список отсеянных техник с причинами, около 97 офлайн-тестов и уже существующий контур оценки: LLM-as-judge по рубрике из 5 критериев, сверку двух судей, калибровку на размеченных данных, замер дрейфа выбора.

3Пробелы и риски

  1. Официальные цели не покрыты оценкой. eval/run.ts вызывает пайплайн без выбора цели. Главная функция последнего коммита ни разу не проходила через судью, сверку или калибровку.
  2. Судья оценивает форму, а не эффект. Собственная калибровка показала: при равной точности судья предпочитает system_prompting. Калибровка проведена на n=3, на одном типе задач (тональность), и судья — та же модель, что генерирует.
  3. Оценки нет в CI. CI запускает только офлайн-тесты с моками. Внутренние промпты (бриф, выбор, судья, синтез) ничем не защищены от регрессий.
  4. Внутренние промпты не версионированы. У наборов правил версия и хеш есть, у собственных промптов пайплайна нет. Результат оценки нельзя привязать к версии промпта.
  5. Недоверенный ввод попадает в сам генератор. Стадия брифа вставляет текст пользователя без границы между данными и инструкциями. Через MCP к нему приклеивается context от других агентов: содержимое файлов и вывод инструментов. Защита добавляется только в готовый промпт, английским суффиксом и по эвристике. Состязательных тестов нет.
  6. Стоимость и надёжность вызовов не учитываются. В трассировку пишется только время, токены не считываются. У HTTP-вызовов нет таймаута и отмены: десктоп обходит это 900-секундным ожиданием. Бюджет ограничивает число вызовов, а не деньги или токены.
  7. Ключ Gemini передаётся в URL. Адреса попадают в логи прокси и трассировку.
  8. Провайдеры генерации и цели не совпадают. Адаптеры есть только для Gemini, OpenAI и Ollama. Промпт для Claude или Grok нельзя прогнать на целевой модели для сквозной проверки.
  9. Документация разошлась с кодом. Корневой README описывает удалённый веб-интерфейс с чекбоксами, устаревшие модели и test-ollama.js. Счётчики тестов в README не совпадают с реальными. Зависимости openai и @google/genai нигде не импортируются.
  10. Растёт стоимость сопровождения. Два интерфейса (веб на Vite и PyQt), монолит desktop/app.py, смесь русского и английского в коде и документации, большой объём незакоммиченной работы.

6Что ещё не учтено

  • Безопасность ключей. По коду сохранения ключа между сессиями не видно; во время работы не проверялось. Если сохранение появится, то только в системном хранилище секретов. Ключи не должны передаваться в URL.
  • Приватность истории. history.sqlite3 хранит потоки мыслей открытым текстом. Нужна политика: очистка, срок хранения, исключение из резервных копий по выбору пользователя.
  • Дрейф официальных гайдов. Скрипты обновления и хеши есть, но обновление ручное. Нужна периодическая проверка, которая сообщает, что источник изменился.
  • Многоязычность. Каркасы техник английские, пользователи пишут по-русски, офлайн-режим даёт смешанный текст. Решить: локализовать шаблоны или убрать офлайн-синтез из основного сценария.
  • Один интерфейс. Решить судьбу веб-интерфейса (index.tsx, LoadingScreen/): поддерживать два интерфейса при одном пайплайне дорого.
  • Таймауты и отмена во всех адаптерах, а не только в десктопе.

7План внедрения

  1. P02–3 дня

    Гигиена

    Закоммитить текущую работу. Переписать корневой README под реальный продукт. Убрать неиспользуемые зависимости и test-*.js. Добавить таймаут и отмену в HTTP-вызовы. Убрать ключ из URL.

    Эффект: репозиторий отражает правду, два операционных риска закрыты.

  2. P0~1 неделя

    Измеримость основного сценария

    Версии и хеши промптов в трассировке (4.3), учёт токенов (4.4), оценка официальных целей (4.1).

    Эффект: каждый балл привязан к версии и цене, официальные цели впервые измерены.

  3. P1~1 неделя

    Регрессионный контур

    Ночной прогон оценки с базовой линией и порогами (4.2). Состязательные задачи и изоляция недоверенного ввода (4.5).

    Эффект: правки промптов перестают быть ставкой вслепую, вход через MCP защищён.

  4. P22–3 недели

    Достоверность оценки

    Проверки по задаче с эталонами (4.6), сквозной прогон на целевых провайдерах (4.7), расширенная калибровка судьи.

    Эффект: можно делать выводы «вариант A лучше B», а не только ловить грубые ошибки.

  5. P3по ходу

    Сопровождение

    Разбить desktop/app.py на модули. Решить судьбу веб-интерфейса. Автоматически проверять дрейф источников правил. Задать политику хранения истории.

Чего не хватает для более уверенных выводов: результатов живого прогона оценки на текущем коде, данных о реальном использовании (какие цели и режимы выбирают) и решения команды, является ли веб-интерфейс продуктом или артефактом.
